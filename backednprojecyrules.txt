api_design_guidelines:

API Design Principles
1. RESTful Standards

Use plural nouns for resource names.

Use predictable, consistent URL patterns.

Use HTTP methods appropriately.

2. Naming Conventions
Action	Method	Example
Get list	GET	/orders
Get one	GET	/orders/:id
Create	POST	/orders
Update	PATCH	/orders/:id
Delete	DELETE	/orders/:id
3. Response Format

Always return:
{
  success: boolean,
  message: string,
  data?: any
}

Example:
{
  success: true,
  message: "Order created successfully",
  data: { orderId: "123" }
}

4. Status Codes

200 → OK

201 → Created

400 → Bad request

401 → Unauthorized

403 → Forbidden

404 → Not found

409 → Conflict

500 → Internal server error

5. Pagination Standard
GET /shops?page=1&limit=20

Response:
{
  success: true,
  message: "Shops fetched",
  data: {
    items: [],
    total: 120,
    page: 1,
    limit: 20
  }
}

6. Validation

Every create/update endpoint must validate DTOs.

Use a dedicated validation layer.

Reject invalid data early.

7. Authentication

Use access tokens + refresh tokens.

Token must be included via Authorization: Bearer <token>.

Protect role-specific routes via middleware.

8. Idempotency

Never process the same order twice.

Ensure crucial endpoints check current state before modifying.

9. Versioning

Prefix APIs with /api/v1/ for future flexibility.

10. Files & Media

Store URLs only.

Avoid storing raw images in DB.

Allow easy switching to S3 or other storage later.

socket_events_reference

Socket.IO Real-Time Event Architecture
Overview

The app uses Socket.IO for real-time updates among:

Customer

Shopkeeper

Rider

Each user joins a room based on identity:

Room Naming
customer:{customerId}
shop:{shopId}
rider:{riderId}


Server Responsibilities

Authenticate socket connection.

Join user to respective rooms.

Emit events from services, not controllers.

Handle reconnection gracefully.

Core Events
1. Customer → Shopkeeper

Event: order:new

Sent when customer places a new order.

Target room: shop:{shopId}

Payload:
{
  orderId,
  customerId,
  items,
  subtotal,
  deliveryCharges,
  total
}

2. Shopkeeper → Customer
Event: order:review-update

Sent when shopkeeper modifies items (some unavailable).

Event: order:confirm-required

Sent when customer must confirm updated total.

Event: order:accepted

Order is accepted.

Event: order:rejected

Order is rejected.

Payload example:

{
  orderId,
  updatedItems?,
  reason?
}


3. Shopkeeper → Rider
Event: rider:assigned

Shopkeeper assigns rider to order.

Sent to: rider:{riderId}
Payload:

{
  orderId,
  shopId,
  pickupLocation,
  dropoffLocation
}

4. Rider → Customer
Event: delivery:started

Rider has begun delivery.

Event: delivery:nearby

Optional event for proximity alerts.

Event: delivery:completed

Order delivered successfully.

Payload:

{
  orderId,
  deliveredAt,
  proofImage?
}

5. Customer → Shopkeeper (Feedback)

Event: order:feedback
Payload:

{
  orderId,
  rating?,
  comments?
}

Socket Acknowledgements

Every event handler should optionally support:

callback({ success: true, message: "Delivered" })

Error Events

Emit structured error packets:

socket.emit("error", {
  code: "ORDER_NOT_FOUND",
  message: "Order does not exist"
})
